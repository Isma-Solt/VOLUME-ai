# Инструкция по серверу: обновление, dev-версия, бот, домен

Написано под конкретно ваш проект: сайт VOLUME, сервер `62.60.251.123`,
Ubuntu + nginx, папка сайта `/var/www/volume`, репозиторий
`https://github.com/Isma-Solt/VOLUME-ai`.

---

## 0. Как устроен ваш проект (чтобы дальше было понятно)

Три отдельные вещи, которые часто путают:

| Что | Где живёт | Зачем |
|---|---|---|
| **Сайт** | `/var/www/volume` на сервере | HTML/CSS/JS, которые видит посетитель |
| **Обработчик заявки** | `/var/www/volume/api/send.php` | Принимает форму и пересылает в Telegram |
| **Бот** | у Telegram на их серверах | Просто «почтовый ящик», куда падает заявка |

Важный момент: **у вас сейчас нет бота как отдельной программы**. Форма на сайте
шлёт данные в `api/send.php`, а тот дёргает Telegram API с вашим токеном.
Никакой процесс на сервере постоянно не крутится. Это нормальная и самая
простая схема — «заливать бота на сервер» в вашем случае означает просто
положить правильный `send.php` и прописать токен. Раздел 4 разбирает и этот
вариант, и настоящий бот-процесс, если он вам когда-нибудь понадобится.

Что изменилось после моей правки:

- Токен бота **больше не лежит в коде**. Он переехал в `/etc/volume/bot.env` —
  файл вне папки сайта. Его нельзя скачать через браузер и нельзя случайно
  закоммитить в GitHub.
- Поэтому папка `api/` теперь хранится в git (раньше была в `.gitignore`), и
  обновления обработчика приезжают на сервер вместе с остальным кодом.
- Появилась папка `deploy/` со скриптами и конфигами.

## ⚠️ Сначала прочитайте это

**Токен бота утёк в публичный репозиторий.** В истории коммитов на GitHub, в
старой версии `js/main.js`, лежит рабочий токен и chat_id — их видит кто угодно.
Удалить из истории уже бесполезно: всё, что попало в публичный git, считается
раскрытым навсегда.

Что сделать прямо сейчас, это одна минута:

1. Откройте `@BotFather` в Telegram
2. `/revoke` → выберите `@VOLUME_autorization_bot`
3. Получите новый токен и используйте его в шаге 1

Пока токен не отозван, любой человек может от имени вашего бота читать заявки
и писать вашим клиентам.

## Быстрый путь: два скрипта вместо ручной настройки

Всё, что описано ниже вручную, собрано в два скрипта. Если хотите разобраться —
читайте разделы по порядку. Если хотите просто чтобы работало:

```bash
# подключиться к серверу
ssh root@62.60.251.123

# скачать скрипт настройки
curl -fsSL -o /root/server-setup.sh \
  https://raw.githubusercontent.com/Isma-Solt/VOLUME-ai/main/deploy/server-setup.sh

# посмотреть, что внутри (полезная привычка перед запуском чужих скриптов)
less /root/server-setup.sh

# запустить
bash /root/server-setup.sh
```

Скрипт спросит новый токен и chat_id, спрячет их в `/etc/volume/bot.env`,
поставит недостающие пакеты, заберёт код с GitHub, настроит nginx и отправит
вам тестовое сообщение в Telegram. Запускать можно повторно — уже настроенное
он не ломает.

Потом, когда захотите dev-версию:

```bash
bash /var/www/volume/deploy/dev-setup.sh
```

## 1. Разовая настройка (делается один раз)

### 1.1 Подключиться к серверу

```bash
ssh root@62.60.251.123
```

Дальше все команды — на сервере.

### 1.2 Спрятать токен в отдельный файл

```bash
mkdir -p /etc/volume

# Посмотрите старый токен и chat_id, они сейчас внутри send.php:
grep -iE "token|chat" /var/www/volume/api/send.php
```

Создаём файл с секретами (подставьте свои значения из вывода выше):

```bash
cat > /etc/volume/bot.env <<'EOF'
BOT_TOKEN=сюда_токен_от_BotFather
CHAT_ID=сюда_ваш_chat_id
EOF

# Читать может только root и веб-сервер, больше никто
chown root:www-data /etc/volume/bot.env
chmod 640 /etc/volume/bot.env
```

`chmod 640` означает: владелец читает и пишет, группа только читает,
все остальные — ничего. Это защита на случай, если на сервере заведётся
другой пользователь или чужой скрипт.

### 1.3 Сохранить старый send.php на всякий случай

```bash
cp /var/www/volume/api/send.php /root/send.php.backup
```

### 1.4 Забрать новый код

Сначала запушьте изменения с компьютера (см. раздел 2.1), потом на сервере:

```bash
cd /var/www/volume
git fetch origin
git reset --hard origin/main
chmod +x deploy/*.sh
```

Если git ругнётся, что `api/send.php` мешает — просто удалите его и повторите:
`rm /var/www/volume/api/send.php && git reset --hard origin/main`
(копия уже лежит в `/root/send.php.backup`).

### 1.5 Проверить, что PHP вообще установлен

```bash
ls /run/php/
```

Должно показать что-то вроде `php8.3-fpm.sock`. **Запомните номер версии** —
он нужен в конфиге nginx. Если папки нет, PHP не установлен:

```bash
apt update && apt install -y php-fpm php-curl
```

### 1.6 Поставить конфиг nginx

```bash
cp /var/www/volume/deploy/nginx/volume.conf /etc/nginx/sites-available/volume

# Если версия PHP не 8.3 — поправьте её в конфиге:
nano /etc/nginx/sites-available/volume

ln -sf /etc/nginx/sites-available/volume /etc/nginx/sites-enabled/volume
rm -f /etc/nginx/sites-enabled/default

nginx -t && systemctl reload nginx
```

`nginx -t` — проверка конфига **до** применения. Всегда запускайте её перед
`reload`: если в конфиге опечатка, nginx не перезапустится и сайт ляжет.

### 1.7 Проверить, что заявки доходят

Откройте сайт, заполните форму, отправьте. Сообщение должно прийти в Telegram.
Если не пришло — смотрим, что случилось:

```bash
tail -30 /var/log/nginx/volume.error.log
```

Три самые частые причины:

- **Вы не нажали Start у бота.** Telegram запрещает боту писать первым.
  Откройте `@VOLUME_autorization_bot` и нажмите «Начать».
- **Неверный `CHAT_ID`.** Как узнать свой — в разделе 4.2.
- **Сервер не достучался до `api.telegram.org`.** Проверьте:
  `curl -s -o /dev/null -w "%{http_code}\n" https://api.telegram.org` —
  должно быть `200`. Если висит или ошибка, значит с вашего сервера Telegram
  недоступен, нужен прокси (раздел 4.4).

## 2. Как обновлять сайт (ваш повседневный цикл)

Правило, которое экономит нервы: **на сервере руками файлы не правим никогда**.
Сервер только забирает готовый код из GitHub. Иначе рано или поздно вы
потеряете правку, которую сделали «быстренько прямо там».

### 2.1 На вашем компьютере: отправить изменения

```bash
cd "C:\Users\Хас строй\Documents\VOLUME-ai_rep"

git status          # посмотреть, что изменилось
git add -A          # взять все изменения
git commit -m "Поменял цены в услугах"
git push origin main
```

`git status` перед коммитом — полезная привычка: видно, не попало ли туда
лишнее.

### 2.2 На сервере: применить

```bash
ssh root@62.60.251.123
/var/www/volume/deploy/update.sh
```

Скрипт `update.sh` делает четыре вещи, и вот зачем каждая:

1. **Архивирует текущий сайт** в `/var/backups/volume/`. Если новая версия
   окажется сломанной, есть куда вернуться. Хранит 10 последних копий.
2. **`git fetch` + `git reset --hard origin/main`** — забирает код с GitHub и
   приводит папку сервера ровно к тому, что в репозитории. `reset --hard`
   жёстче, чем `git pull`: он не пытается сливать изменения, а просто делает
   «как на GitHub». Именно это и нужно на сервере.
3. **Выставляет права** `www-data` — от этого пользователя работает nginx.
   Без этого PHP может не прочитать свои же файлы.
4. **Проверяет и перезагружает nginx.**

### 2.3 Если что-то сломалось

```bash
/var/www/volume/deploy/rollback.sh
```

Вернёт последнюю рабочую копию, а сломанную отложит в `/var/www/volume.broken`,
чтобы можно было потом разобраться, что пошло не так.

## 3. Dev-версия сайта

### Что это и зачем

Dev-версия — **вторая копия сайта на том же сервере**, на которой вы
экспериментируете. Посетители в это время сидят на боевой версии и ничего не
замечают. Сломали dev — не страшно, это и есть его работа.

У вас будет так:

- `ваш-домен.ru` → `/var/www/volume` → ветка `main` → боевой сайт
- `dev.ваш-домен.ru` → `/var/www/volume-dev` → ветка `dev` → полигон

### 3.1 Завести ветку dev

На компьютере:

```bash
cd "C:\Users\Хас строй\Documents\VOLUME-ai_rep"
git checkout -b dev
git push -u origin dev
```

Ветка — это параллельная версия кода. `main` остаётся нетронутой, пока вы
возитесь в `dev`.

### 3.2 Развернуть копию на сервере

```bash
git clone https://github.com/Isma-Solt/VOLUME-ai.git /var/www/volume-dev
cd /var/www/volume-dev
git checkout dev
chown -R www-data:www-data /var/www/volume-dev
```

### 3.3 Отдельный конфиг для заявок

Чтобы тестовые заявки не сыпались вам вперемешку с настоящими:

```bash
cp /etc/volume/bot.env /etc/volume/bot-dev.env
nano /etc/volume/bot-dev.env    # можно поставить другой CHAT_ID
chown root:www-data /etc/volume/bot-dev.env
chmod 640 /etc/volume/bot-dev.env
```

Конфиг nginx для dev уже передаёт в PHP метку `VOLUME_ENV=dev`, а `send.php`
по этой метке сам выбирает `bot-dev.env`. Ничего править в коде не нужно.

### 3.4 Закрыть dev паролем

Чтобы недоделанную версию не увидели посторонние и не проиндексировал Яндекс:

```bash
apt install -y apache2-utils
htpasswd -c /etc/nginx/.htpasswd-dev admin
# введите пароль дважды
```

### 3.5 Включить dev-сайт

```bash
cp /var/www/volume-dev/deploy/nginx/volume-dev.conf /etc/nginx/sites-available/volume-dev
nano /etc/nginx/sites-available/volume-dev   # вписать свой домен в server_name
ln -sf /etc/nginx/sites-available/volume-dev /etc/nginx/sites-enabled/volume-dev
nginx -t && systemctl reload nginx
```

**Если домена ещё нет**, поддомен сделать не из чего. Временный вариант —
повесить dev на отдельный порт: в конфиге замените `listen 80;` на
`listen 8080;`, уберите строку `server_name`, и dev откроется по адресу
`http://62.60.251.123:8080`.

### 3.6 Рабочий цикл

```bash
# на компьютере: правим в ветке dev
git add -A && git commit -m "Пробую новый блок" && git push origin dev

# на сервере: обновляем dev
/var/www/volume-dev/deploy/update-dev.sh

# посмотрели, всё нравится — переносим в боевую версию
git checkout main
git merge dev
git push origin main

# на сервере
/var/www/volume/deploy/update.sh
```

## 4. Бот

### 4.1 Что у вас сейчас

Повторю, потому что это главное недоразумение в теме: **отдельного бота на
сервере у вас нет и не нужно**. Есть токен и `send.php`, который этим токеном
отправляет сообщение. Всё «заливание бота» сводится к разделу 1.2 — положить
токен в `/etc/volume/bot.env`.

### 4.2 Как узнать свой chat_id

Напишите что-нибудь боту `@VOLUME_autorization_bot` в Telegram, потом на
сервере:

```bash
source /etc/volume/bot.env
curl -s "https://api.telegram.org/bot$BOT_TOKEN/getUpdates" | head -c 2000
```

В ответе найдите `"chat":{"id":123456789` — это и есть ваш `CHAT_ID`.

### 4.3 Если нужен настоящий бот-процесс

Понадобится, когда бот должен **сам что-то делать**: отвечать на команды,
слать напоминания, вести диалог. Тогда это программа, которая крутится
постоянно. В `deploy/bot/` лежит заготовка.

```bash
# 1. Кладём код
mkdir -p /opt/volume-bot
cp /var/www/volume/deploy/bot/bot.py /opt/volume-bot/
chown -R www-data:www-data /opt/volume-bot

# 2. Ставим службу
cp /var/www/volume/deploy/bot/volume-bot.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now volume-bot

# 3. Проверяем
systemctl status volume-bot
journalctl -u volume-bot -f      # живые логи, выход по Ctrl+C
```

Что здесь важно понять:

- **systemd** — встроенный в Ubuntu «менеджер программ, которые должны
  работать всегда». Просто запустить `python3 bot.py` в терминале нельзя:
  закроете SSH — бот умрёт.
- **`Restart=always`** в юните — если бот упадёт с ошибкой, система поднимет
  его через 5 секунд сама.
- **`enable`** — бот стартует после перезагрузки сервера. **`--now`** —
  и прямо сейчас тоже.
- Логи смотрятся через `journalctl -u volume-bot`, а не в файлах.

Обновление бота после правок:

```bash
cp /var/www/volume/deploy/bot/bot.py /opt/volume-bot/ && systemctl restart volume-bot
```

### 4.4 Если Telegram с сервера недоступен

Проверка:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://api.telegram.org
```

`200` — всё хорошо, ничего делать не надо. Если висит или пусто, у сервера нет
доступа к Telegram. Варианты: перенести сервер к хостеру за пределами РФ
(судя по IP, у вас, похоже, так и есть) либо пустить запросы через прокси.

### 4.5 Правило про токен

Если токен хоть раз попал в GitHub, в скриншот или в переписку — **считайте
его скомпрометированным**. Откройте `@BotFather` → `/revoke` → выберите бота →
получите новый токен → пропишите в `/etc/volume/bot.env`. Это занимает минуту
и всегда дешевле, чем разбираться с последствиями.

Кстати: скриншот с приватным SSH-ключом в `Documents/server_ssh_key/` — по той
же причине лучше сгенерировать пару заново и старую отозвать.

## 5. Домен

### 5.1 Купить

Смотрите не на цену первого года, а на **цену продления** — разница бывает в
разы. По актуальному сравнению: SpaceWeb ~189 ₽ регистрация и ~319 ₽
продление — оптимально; 2domains дешевле на входе (~149 ₽), но продление
~849 ₽; RU-CENTER при ~219 ₽ на входе берёт ~3075 ₽ за продление.

Берите только у аккредитованного регистратора (список на `cctld.ru`) — иначе
потом будет больно переносить домен.

### 5.2 Направить на сервер

В панели регистратора, в разделе DNS, добавьте три записи:

| Тип | Имя | Значение |
|---|---|---|
| A | `@` | `62.60.251.123` |
| A | `www` | `62.60.251.123` |
| A | `dev` | `62.60.251.123` |

Запись `A` — это «такое-то имя ведёт на такой-то IP». Изменения расходятся по
интернету от 15 минут до нескольких часов.

Проверить, что дошло:

```bash
nslookup ваш-домен.ru
```

### 5.3 Вписать домен в nginx

```bash
nano /etc/nginx/sites-available/volume
# заменить  server_name _;
# на        server_name ваш-домен.ru www.ваш-домен.ru;

nginx -t && systemctl reload nginx
```

### 5.4 Включить HTTPS (бесплатно)

Без замочка в адресной строке браузеры показывают «Не защищено», а формы с
персональными данными по HTTP — плохая идея и с точки зрения закона.

```bash
apt install -y certbot python3-certbot-nginx
certbot --nginx -d ваш-домен.ru -d www.ваш-домен.ru -d dev.ваш-домен.ru
```

Certbot сам получит сертификат, сам пропишет его в конфиги nginx и сам будет
продлевать каждые 90 дней. Проверить, что автопродление работает:

```bash
systemctl status certbot.timer
```
